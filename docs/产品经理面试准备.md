# AI硬件选型助手 · 产品经理面试准备

> 写给未来的自己：面试官要的不是"你有真实数据"，而是"你知道数据从哪来、为什么这么做、怎么验证"。

---

## 一、一页纸产品陈述

### 30 秒版

> 我做了一个 AI 硬件选型助手：学生用大白话描述需求（比如"做个低功耗蓝牙温湿度传感器"），AI 自动解析参数、从 100 个真实元器件的知识库里检索推荐（附理由、价格、Datasheet），确认后一键生成 BOM 并导出 Excel/CSV。核心解决三个问题：新手看不懂参数筛选器、ChatGPT 推荐会编型号、选完型还要手动做物料清单。

### 1 分钟版（增加"为什么可信"）

> 市面上选型工具分两类：立创/DigiKey 的参数筛选器门槛高，ChatGPT 能聊但会幻觉——推荐不存在的型号。我的产品用 RAG 技术让 AI 只能从知识库真实型号里选，每次推荐都和数据库交叉验证，附官方 Datasheet 链接可核实。交付物不是参数表格，而是可直接采购的 BOM 清单。技术栈是 Next.js + FastAPI + DeepSeek + 向量检索，MVP 已完整跑通。

## 二、用户与痛点

| 用户 | 场景 | 痛点 |
|------|------|------|
| 高校电子专业学生（核心） | 课程设计 / 电赛 / 毕设 | 不知道选什么、不会查参数、预算敏感、时间紧 |
| 有经验的硬件开发者（次核心） | 提高选型效率 | 参数筛选器繁琐、想快速对比 |
| 硬件课程教师（潜在） | 给学生推荐方案 | 难以给学生结构化的选型建议 |

**一句话痛点**：学生选型靠"师兄用什么我买什么"，碰运气。

## 三、功能决策表（功能 → 痛点 → 产品承诺）

| 功能 | 解决什么痛点 | 产品承诺 |
|------|-------------|---------|
| 自然语言输入 | 新手看不懂几百个参数筛选器 | 低门槛：说人话就能选型 |
| 参数解析 + 可修改确认页 | AI 可能理解错，用户需要掌控感 | 可信：AI 可被纠正 |
| 推荐理由 + 匹配度徽章 | "为什么推荐它"说不清就没人敢买 | 透明：每个推荐都讲理由 |
| RAG 防幻觉 + Datasheet 链接 | ChatGPT 会编造不存在的型号 | 可靠：只推真型号，可核实 |
| 价格/库存/供应商同卡呈现 | 学生预算敏感，选完还要比价 | 决策闭环：不跳转 |
| 一键生成 BOM + 导出 Excel/CSV | 选完型还要手动做物料清单 | 效率：想法 → 采购清单 |
| 一键全部加入 BOM | 学生常"全都要"，逐个点累 | 效率细节 |
| 免登录 | 注册是学生流失的最大坎 | 零摩擦 |

## 四、技术决策表（技术 → 支撑的产品承诺 → 取舍）

| 技术 | 支撑的承诺 | 为什么不是别的 |
|------|-----------|---------------|
| RAG（先检索再生成） | 防幻觉、可信 | 纯 LLM 会编型号；RAG 让 AI 只能从真库选 |
| 向量检索（ChromaDB + 中文嵌入模型） | 懂意图 | 关键词搜不到"温湿度"与"测温度和湿度"的语义关联 |
| LLM 结构化输出（JSON） | 低门槛 + 可用 | 自然语言进、结构化参数出，下游好处理 |
| 型号交叉验证（SQLite） | 可信 | 即使 LLM 胡说，最终数据以数据库为准 |
| DeepSeek API | 成本可控的中文理解 | 比 Claude/GPT 便宜，中文质量好 |
| SQLite + ChromaDB | MVP 速度 | 零配置本地跑，先验证需求再上重型库 |

**主动讲取舍（PM 思维的体现）**：
- 为什么没用 LangChain？只有两个调用场景，框架复杂度大于收益——做减法。
- 为什么先只做 100 个元器件？先验证流程，再谈规模——先跑通再优化。
- 为什么 MVP 不做登录/方案保存/元件对比？P1 功能，核心价值验证优先级更高。

## 五、UI 决策表（界面元素 → 用户心理依据）

| UI 设计 | 依据 |
|---------|------|
| 四步向导（输入→确认→推荐→BOM） | 拆解复杂流程，降低认知负担，新手知道"从哪开始" |
| 参数确认页放中间且可编辑 | 人机协作而非机器独裁，用户觉得可控，AI 可纠正 |
| 匹配度三色徽章（绿/蓝/黄） | 信息分层，扫一眼即知优先级，不用读完所有卡片 |
| 推荐理由 + 左侧色条 | 透明 = 信任，讲清"为什么适合你" |
| 价格/库存/Datasheet/采购同卡 | 决策信息一次给全，减少跳转流失 |
| 骨架屏 + 进度条 | LLM 响应 15-30 秒，感知性能设计让等待显快 |
| 免登录 + 移动端适配 | 学生手机访问为主，注册是流失点 |
| 靛蓝主色（从紫色迭代而来） | 更专业/工程感，契合硬件工具气质 |

## 六、指标与验证计划（没有数据时的武器）

### 北极星指标
**从输入到生成 BOM 的完成率**

### 关键漏斗（上线埋点）
进入首页 → 完成解析 → 点击推荐卡片 → 生成 BOM → 导出

### 关键行为与假设
| 行为 | 如果偏高说明 | 优先动作 |
|------|-------------|---------|
| "修改参数"点击率 | 解析质量差 | 调优 LLM prompt / 增加纠错样本 |
| 推荐卡片点击率 | 推荐相关性差 | 调整检索排序 / 扩充知识库 |
| 生成 BOM 后导出率 | 闭环价值成立 | 继续强化导出体验 |
| 中途流失位置 | 该环节体验差 | 针对性优化 |

### 小规模验证方案（面试杀手锏）
1. 去学校实验室/社团找 10 个正在做课程设计或电赛的同学，现场演示并观察卡点
2. 用"电赛前两周"场景冷启动——学生最缺时间，最需要快速选型
3. "人工客服版"需求验证：在校园群手动帮人推荐元器件，有人天天问 = 需求真实
4. 问卷/小红书收集"选型最痛的事"，作为 PRD 修订依据

## 八、面试 Q&A（把攻击变成展示）

| 质疑 | 应答 |
|------|------|
| "没有用户数据，是不是自嗨？" | 承认没有规模化数据，但有调研结论 + 完整埋点/验证计划，下一步就是小规模验证。 |
| "ChatGPT 也能做，优势是什么？" | ChatGPT 会编型号；我用 RAG + 数据库交叉验证保证只推真型号，附 Datasheet 可核实。选型场景"可信"比"能聊"重要。 |
| "和立创/DigiKey 比呢？" | 他们面向会查参数的工程师；我服务被筛选器劝退的学生，入口是自然语言，交付是 BOM。 |
| "为什么不做登录？" | MVP 先验证核心价值，登录增加流失；保存方案是 P1，等留存假设要验证时再做。 |
| "100 个元器件够用吗？" | 够验证流程，不够商用；路线图是按品类规模化 + 接真实价格 API。 |
| "LLM 幻觉怎么办？" | 三层防幻觉：只从检索结果选、型号与 SQLite 交叉验证、参数以数据库为准。 |
| "为什么用 DeepSeek？" | 成本可控、中文好；后续可切换 Claude/GPT，接口已抽象。 |

## 十、一句话总结

**这个产品不是"自嗨"——它是在一个被忽视的群体（学生）和一个被验证的痛点（选型难、不信任 AI）之间，用"可信的 AI"填补的缝隙。没有数据不可怕，可怕的是不知道数据从哪里来。**
