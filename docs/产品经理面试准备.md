# AI硬件选型助手 · 产品经理面试准备

> 写给未来的自己：面试官要的不是"你有真实数据"，而是"你知道数据从哪来、为什么这么做、怎么验证"。

---

## 一、一页纸产品陈述

### 30 秒版

> 我做了一个 AI 硬件选型助手：学生用大白话描述需求（比如"做个低功耗蓝牙温湿度传感器"），AI 自动解析参数、从 100 个真实元器件的知识库里检索推荐（附理由、价格、Datasheet），确认后一键生成 BOM 并导出 Excel/CSV。核心解决三个问题：新手看不懂参数筛选器、ChatGPT 推荐会编型号、选完型还要手动做物料清单。

### 1 分钟版（增加"为什么可信"）

> 市面上选型工具分两类：立创/DigiKey 的参数筛选器门槛高，ChatGPT 能聊但会幻觉——推荐不存在的型号。我的产品用 RAG 技术让 AI 只能从知识库真实型号里选，每次推荐都和数据库交叉验证，附官方 Datasheet 链接可核实。交付物不是参数表格，而是可直接采购的 BOM 清单。技术栈是 Next.js + FastAPI + DeepSeek + 向量检索，MVP 已完整跑通。

| 用户 | 场景 | 痛点 |

| 高校电子专业学生（核心） | 课程设计 / 电赛 / 毕设 | 不知道选什么、不会查参数、预算敏感、时间紧 |

**一句话痛点**：学生选型靠"师兄用什么我买什么"，碰运气。

### 深挖：立创/DigiKey 参数筛选器门槛为什么高？

> 不是"因为没有 AI"，而是**筛选器默认用户已经懂行**——它只帮你"缩小范围"，不帮你"建立问题"。

四个层次：

| 层次 | 内容 | 例子 |
|------|------|------|
| 知识层 | 不知道该筛什么参数 | 学生不知道"待机电流/接口/封装"是关键维度 |
| 语言层 | 术语是墙 | DigiKey 几百个英文参数项，学生看不懂 |
| 翻译层（最关键） | 功能需求 → 参数约束的翻译 | "测温湿度+蓝牙传手机" → "I2C + 低功耗 MCU + BLE" |
| 判断层 | 参数相近时选哪个 | 筛选器给事实清单，不给"为什么适合你" |

**产品定位话术**：

> "门槛高不是因为没有 AI，而是筛选器把'翻译'这个隐形成本留给了用户。我们把翻译层交给 AI（自然语言→结构化参数），把判断层用推荐理由+匹配度补上，把信任层用参数确认页+Datasheet 链接兜住。AI 只是手段之一，不是全部。"

**被追问"立创/DigiKey 也有 AI 了"时的应答**：

> "他们的 AI 是搜索增强——帮你更快查参数，入口仍是'元器件检索'，默认你知道要查什么。我们的定位是从想法到 BOM 的完整闭环：功能级描述进、可采购清单出，聚焦学生这个被忽视的群体。"

## 四、技术决策表（技术 → 支撑的产品承诺 → 取舍）

| 技术 | 支撑的承诺 | 为什么不是别的 |
|------|-----------|---------------|
| RAG（先检索再生成） | 防幻觉、可信 | 纯 LLM 会编型号；RAG 让 AI 只能从真库选 |
| 向量检索（ChromaDB + 中文嵌入模型） | 懂意图 | 关键词搜不到"温湿度"与"测温度和湿度"的语义关联 |
| LLM 结构化输出（JSON） | 低门槛 + 可用 | 自然语言进、结构化参数出，下游好处理 |
| 型号交叉验证（SQLite） | 可信 | 即使 LLM 胡说，最终数据以数据库为准 |
| DeepSeek API | 成本可控的中文理解 | 比 Claude/GPT 便宜，中文质量好 |
| SQLite + ChromaDB | MVP 速度 | 零配置本地跑，先验证需求再上重型库 |

**主动讲取舍（PM 思维的体现）**：
- 为什么没用 LangChain？只有两个调用场景，框架复杂度大于收益——做减法。
- 为什么先只做 100 个元器件？先验证流程，再谈规模——先跑通再优化。
- 为什么 MVP 不做登录/方案保存/元件对比？P1 功能，核心价值验证优先级更高。

### RAG 深度拆解（面试核心素材）

**一句话**：RAG = 先检索真实资料，再让 AI 基于资料作答，把 AI 的自由度锁死。

**流程**：
用户需求 → LLM 解析成结构化参数 → 向量检索(ChromaDB Top30) + 关键词检索(Top30) 合并 → 结构化过滤(电压/接口/品类) → LLM 只排序+写理由（禁编型号）→ SQLite 交叉验证 → Top5 输出

**每个环节为什么**：
| 环节 | 为什么 |
|------|--------|
| 先解析成结构化参数 | 才能做硬性过滤（电压/接口），且参数确认页让用户可纠错（信任机制） |
| 向量检索 | 语义理解："温湿度"与"测温度和湿度"字面不同但语义相近 |
| 关键词检索合并 | 向量检索会品类失衡（实测：小车查询 Top30 里 18 个电源芯片），双路合并保覆盖 |
| 结构化过滤 | 硬指标（不行就是不行）交给规则，AI 只做软判断（排序/理由） |
| LLM 只排序不生成 | 防幻觉核心：prompt 锁定"只能从候选选，不能编型号" |
| 型号交叉验证 | 最后防线：查不到就丢弃，用户看到的永远是真型号 |
| Top5 | 决策负担平衡：够比又不累 |

**防幻觉三层**：候选约束（只从检索结果选）→ 型号验证（SQLite 交叉验证）→ 数据为准（参数/价格/Datasheet 全从库取）。

**面试 30 秒话术**：

> "我的 RAG 设计核心是把 AI 的自由度锁死：向量+关键词双路检索拿 30 个真实候选，结构化过滤硬性指标，LLM 只做排序和写理由，最后型号再过数据库验证。用户看到的每个推荐都来自真实知识库、附可核实的 Datasheet——这是'可信'这个产品承诺的工程实现。过程中我踩过品类失衡的坑，通过双路检索合并解决。"

### 向量检索（ChromaDB + 中文嵌入模型）大白话版

**三样东西：**
- **向量 = 文字的"数字指纹"**：一段文字变成 384 个数字，是它的独特标记
- **嵌入模型 = 造指纹的机器**：被训练成"意思相近的文字，指纹也相近"
- **ChromaDB = 存指纹的图书馆**：存指纹 + 回答"我的指纹和谁最像"（近邻检索 Top K）

**为什么不用普通搜索：**

| | 关键词搜索 | 向量检索 |
|--|-----------|---------|
| 原理 | 字面一样才搜得到 | 意思相近就找得到 |
| 例子 | 搜"温湿度"找不到"测温度和湿度" | 能找到 |
| 一句话 | 认字 | **认意思** |

**面试大白话版：**

> "向量检索就是把文字变成数字指纹，意思相近的文字指纹也相近。我把 100 个元器件的描述都转成指纹存进数据库，用户提问时把问题也转成指纹，让数据库找出最像的 30 个候选。这样用户说'温湿度传感器'，系统也能找到描述里写'测温度和湿度'的元器件——关键词搜索做不到这种'认意思'的能力。"

**专业版：**

> "我用 sentence-transformers 的多语言嵌入模型（paraphrase-multilingual-MiniLM-L12-v2）把元器件描述和用户需求编码成 384 维向量，用余弦相似度做语义匹配，ChromaDB 做近邻检索返回 Top K 候选；同时保留关键词检索做双路融合，因为纯向量检索实测会品类失衡。"

**被追问备弹：**
| 追问 | 回答 |
|------|------|
| 为什么 384 维？ | 模型定长输出，够表达语义且计算快，MVP 够用 |
| 为什么用多语言模型？ | 产品中文优先但也要接英文需求 |
| 向量检索的缺点？ | 找"像的"不找"对的"，可能品类失衡/召回不全，所以加关键词兜底 + 结构化过滤 |

### 从零搭建 RAG 的步骤清单（面试"你会怎么做"题）

**总览**：知识库（数据）→ 索引（让机器能找）→ 生成（AI 基于找到的答）

1. **备数据**：每个元器件准备结构化字段（型号/价格/电压/接口/Datasheet）+ 一段 100-200 字高质量中文描述
2. **选嵌入模型**：把描述文本转成向量（机器只能比较数字，不能比较文字）
3. **存向量库**：向量+元数据存进 ChromaDB，之后能回答"谁和我最像"
4. **查询检索**：用户需求用**同一个模型**转向量 → Top K 近邻候选（建库和查询必须同一模型）
5. **结构化过滤**：电压/接口/品类硬指标规则过滤
6. **LLM 排序**：需求+候选交给 LLM，prompt 锁定"只能从候选选，不许编型号"
7. **交叉验证**：型号回 SQLite 查，查不到丢弃；价格/参数/Datasheet 从库取

**为什么需要嵌入模型（三个递进理由）**：
1. 计算机不认识文字，只认数字 → 必须先转成向量
2. 关键词匹配太笨：用户描述与元器件描述几乎永远字面不一样
3. 嵌入模型"意思相近→数字相近"，能认意思不认字

**还需要什么**：向量数据库（ChromaDB）、LLM（DeepSeek）、关系库（SQLite）、高质量描述文本（决定检索上限）、Prompt（锁自由度）、过滤逻辑、验证机制。

**面试话术**：

> "三步走：备数据（结构化字段+高质量中文描述）→ 建索引（嵌入模型转向量存 ChromaDB）→ 搭查询链路（需求转向量检索 TopK → 结构化过滤 → LLM 从候选排序写理由 → 型号回库验证）。注意三个坑：建库和查询必须同一嵌入模型；描述文本质量决定检索上限；纯向量检索会品类失衡，加关键词兜底。"

### RAG 组件全家福（七件套逐讲）

| 组件 | 类比 | 在流水线里干什么 | 面试一句话 |
|------|------|----------------|-----------|
| 向量数据库 ChromaDB | 按指纹找书的图书管理员 | 存向量，按相似度近邻检索 Top K | "ChromaDB 负责近邻检索，轻量零配置适合 MVP，架构预留升级空间" |
| LLM DeepSeek | 动脑子的 | 解析自然语言→结构化参数；从候选排序+写理由 | "LLM 负责生成环节，检索靠向量库、判断靠 LLM，各司其职" |
| 关系库 SQLite | 档案室 | 存结构化字段；型号交叉验证；存 BOM | "向量库管找、SQLite 管真，展示数据以档案室为准" |
| 高质量描述文本 | 书上的简介 | 决定检索上限（垃圾进垃圾出） | "描述质量是产品问题不是技术问题，按规范撰写" |
| Prompt | 给实习生划边界 | 锁死 LLM 自由度：只能从候选选、输出 JSON | "Prompt 是第一道闸，把 LLM 限定在排序和写理由" |
| 过滤逻辑 | 硬约束 | 电压/接口/品类规则过滤，不行就是不行 | "硬指标交给规则，可解释可测试，LLM 只做软判断" |
| 验证机制 | 海关安检 | 型号回 SQLite 查，查不到丢弃；展示数据以库为准 | "防幻觉最终兜底，LLM 改不了任何关键数据" |

**流水线一句话**：好的素材（描述）→ 找得像（向量）→ 筛得对（规则）→ 判得准（LLM+Prompt）→ 验得严（SQLite）——这就是"可信的 AI 选型"的全部工程支撑。

### 专业版技术详解（面试被追问时用）

**嵌入模型原理**：Transformer 编码器：分词 → 自注意力编码 → 池化（CLS/mean pooling）→ 固定 384 维向量。训练用对比学习：语义相近句对拉近、相异推开 → 语义相似度≈余弦相似度 `cos(a,b)=a·b/(|a||b|)`。选 MiniLM：蒸馏架构、CPU 可跑、多语言、384 维够用且省内存。建库与查询必须同一模型。

**向量库原理（ChromaDB）**：精确 KNN 是 O(n·d)，量大就慢；用 ANN 近似检索。Chroma 默认 HNSW（分层可导航小世界图）：多层图，高层粗搜低层精搜，检索近 O(log n)。核心概念：PersistentClient（本地持久化）、Collection（向量+文档+metadata）、`where` 元数据过滤、n_results=Top K、距离度量 cosine/l2/ip。规模大了换 Milvus/Qdrant/Pinecone，调用方式不变。

**RAG 两阶段（行业标准）**：
- 离线 Indexing：数据源→清洗→分块→嵌入→入库
- 在线 Retrieval+Generation：查询理解 → 双路检索（dense+sparse，行业用 RRF 倒数排名融合）→ 过滤（元数据+结构化硬过滤）→ 重排（行业用 cross-encoder；本项目用 LLM 排序+理由）→ 生成（prompt 组装）→ 校验
- 为什么双路：稠密懂语义漏精确词、稀疏懂字面不懂语义，互补
- 为什么重排：ANN 是近似召回，Top K 有噪声，精排提升 precision

**LLM 调用（DeepSeek）**：OpenAI 兼容 Chat Completions：`model=deepseek-chat`、`messages` 角色结构、`temperature=0.2`（确定性优先）、`max_tokens`。本项目两次调用（解析→结构化参数；排序→JSON 数组），严格串行依赖。JSON 可靠性：prompt 限格式 + 代码容错（剥代码围栏、从首 `{`/`[` 截取）。生产会加 JSON mode、重试降级、缓存限流。

**SQLite 角色**：嵌入式关系库，单文件零服务，ACID 事务，B-tree 存储，支持 WAL。双库分工：ChromaDB=语义索引（找），SQLite=事实源（真）。展示字段（价格/参数/Datasheet）全从 SQLite 取；交叉验证 `WHERE part_number=?` 查无此号即丢弃。

**过滤逻辑**：确定性规则（电压范围/接口集合/品类）可解释、可测试、零成本；模型只做软判断（排序/理由）。先过滤再排序：减少噪声、省 token、可审计。

**验证机制（guardrails）**：Schema 校验（Pydantic）→ 实体落地（型号回库查询）→ 数据溯源（展示字段来自数据库）→ 兜底（单条丢弃/全空提示）。理念：生成自由，出口受控。

**行业实践对照**：企业 RAG 做数据接入（PDF/网页解析、分块）、混合检索+RRF+cross-encoder 重排、RAGAS 评估（Faithfulness/答案相关/上下文精度）、trace 可观测、缓存限流。检索评估指标：Recall@K、MRR、NDCG。**共识：上线前必须做评估，否则召回差都不知道差在哪。**

**追问应答结构**：定义 → 机制 → 为什么这么选 → 取舍 → 怎么验证。不会的细节：诚实+框架化（"这块我了解机制但没深入源码，让我做会从 XX 入手"）。

### "RAG 防幻觉 + Datasheet 链接"为什么是双保险

**核心逻辑**：选型是信任成本极高的决策（买错元件 = 浪费时间金钱）。用户有两个不信任：

1. AI 会不会编型号？ → RAG 防幻觉（系统端）
2. 推荐是不是真的，凭什么信你？ → Datasheet 链接（用户端可查证）

> "RAG 防幻觉 = 让系统不说谎；Datasheet = 让用户能自己查证。"

**防幻觉三层**：候选约束（LLM 只能从检索结果选）→ 型号交叉验证（SQLite 查不到即丢弃）→ 数据为准（价格/参数/**Datasheet 链接**全从数据库取，连链接都是数据库给的，不是 LLM 生成的）。

**Datasheet 是产品设计而非附属功能**：
- 可验证性建立信任：把验证权交给用户
- 降低验证成本：按钮递到眼前，验证从"额外动作"变"零成本动作"
- 对比：ChatGPT 给不出可信链接；筛选器有但用户得自己找；我们主动给

**面试 30 秒话术**：

> "选型是信任成本极高的决策，我用双保险解决信任：RAG 让 AI 只能从真实知识库选（三层防幻觉），Datasheet 按钮让用户一键核实官方手册。一个是'系统不说谎'，一个是'用户能自己查证'。ChatGPT 敢编型号，筛选器不会说谎但门槛高——我们把'可信'和'低门槛'结合了。"

**加分延伸**：

> "链接真实性依赖人工维护，是数据质量成本，所以知识库标注了'仅供参考、需人工核对'。未来升级方向是 Datasheet 内容解析（RAG over PDF），让用户直接问'这款芯片支持几个 UART'，把信任从'链接可点'升级到'内容可查'。"

### 大白话版（面试前必读，给外行也能听懂）

**前提：AI 会一本正经地胡说八道。** ChatGPT 不懂真假，只会猜一个看起来合理的答案——可能编出根本不存在的型号，这叫"幻觉"。对选型产品是致命的（买不到/买错烧板子）。

**RAG = 开卷考试。** 系统有 100 个真实元器件的"真货清单"。用户提问后：先从清单里捞出最相关的几个 → 告诉 AI"你只能从这几个里选，不许自己编"。闭卷考会瞎写，开卷考限定材料就没法编。

**防幻觉 = 三道保险：**
1. 规定：告诉 AI 只能从候选里选
2. 核对：AI 选完，程序拿型号回数据库查，查不到就扔掉
3. 数据说了算：价格/参数/链接全从数据库拿，AI 只写推荐理由

**Datasheet = 官方说明书。** 厂商发布的最权威技术手册。每条推荐卡片上有按钮，点开就是官方 PDF，用户自己核对"型号是不是真的、参数有没有瞎写"。

**为什么必须组合（买零件比喻）：**
- 只有 RAG：导购只说"这是真货"，空口无凭
- 只有链接：导购满嘴跑火车，链接再真也没用
- 两个都有：导购只从真货里推荐，还把官方说明书递到你手里——既能信他，又能自己验证

**面试大白话话术：**

> "AI 会编造不存在的型号，对选型产品是致命的。所以我做两件事：一是 RAG——从 100 个真实元器件里捞候选，让 AI 只能从候选里选，选完回数据库核对，查不到就丢弃，用户看到的永远是真实型号；二是每条推荐附厂商官方手册链接，用户点一下就能自己核实。一个是保证系统不说假话，一个是给用户亲眼验证的证据。"

## 八·补：没上线怎么办（核心话术）

### 心态：把"没上线"从缺陷翻译成决策

- ❌ 不要说："我还没来得及上线"
- ✅ 要说："我**有意**先不做规模化上线——先验证'学生选型难+不信任 AI'这个核心假设，而不是铺量。MVP 是验证假设的最小闭环，不是产品完成态。"

### 三句话结构（背下来）

1. **定位**："这个产品目前是 MVP 状态，没有正式上线，我把它当作验证假设的最小闭环。"
2. **证据**："做之前我做了用户访谈和竞品调研，核心假设是'新手被参数筛选器劝退、又不信任 AI 推荐'；每个功能都对应这个假设——比如参数确认页可修改，就是为了解决'AI 可能理解错'的信任问题。"
3. **下一步**："上线后第一件事不是推广，而是验证漏斗：埋点'输入→解析→点推荐→生成BOM→导出'，重点看'修改参数'点击率和'生成BOM后导出率'；同时规划了 10 人校园可用性测试。验证不通过就回到调研阶段，而不是继续堆功能。"

### 问法应对速查

| 问法 | 应答 |
|------|------|
| "上线了吗？" | "没有，当前是 MVP。我选择先验证核心价值，避免在没验证需求前过度投入——这本身是个产品决策。" |
| "没数据怎么证明有人需要？" | "没有规模化数据，但有两条证据链：访谈+竞品调研的定性结论；完整的验证方案（埋点漏斗+可用性测试）。数据是用来验证假设的，我现在正是要去拿它。" |
| "这不就是自嗨吗？" | "自嗨是没有目标用户的自我满足。我的每个功能都对应一个用户痛点和一条验证路径，所以它更像一个'待验证的假设'，而验证正是下一步要做的事。" |
| "给你三个月重做，改什么？" | "更早做小规模访谈验证而不是先写代码；把'解析质量'评估指标前置而不是上线后才埋点。这体现我对 0→1 顺序的复盘。" |

## 十、一句话总结

## 十一、知识库数据量问题（"100 个够吗？全世界元器件怎么办？"）

### 核心认知

- 100 个不够商用，但**够验证流程**；"收集全世界元器件"是错误目标——连立创/DigiKey 都不是全量，只收录供应商在售的
- 竞争不靠数量，靠"**找得到 + 信得过**"
- **数据质量 > 数据数量**：错误型号/失效链接会摧毁"可信"这一核心卖点；1000 个没审核的数据比 100 个精挑细选的数据更危险

### 为什么不是全量

1. **80/20**：课程设计/电赛常用型号高度集中（STM32/ESP32/Arduino/常见传感器），300-500 个可覆盖大部分学生场景；长尾不是核心用户场景
2. **质量有成本**：可信是立身之本，堆量是在拿核心资产冒险
3. **赢不了数量战**：数量上永远输给立创，差异化在入口（自然语言）和信任（防幻觉+Datasheet）

### 扩展三策略

| 策略 | 做法 |
|------|------|
| 按场景扩展 | 覆盖 20 个常见场景（温湿度/小车/手环/空气质量/门禁…），每场景配齐 主控+传感器+电源+通信；用户搜索信号驱动补录优先级 |
| 数据管道 | 接商城开放接口批量获取 → LLM+规则生成描述 → 人工抽检 → 自动同步价格；build_kb.py 已支持增量导入 |
| 需求信号入口 | 搜不到时让用户提交缺失型号 = 补录优先级 = 社区化扩充开端 |

### 路线图数字

| 阶段 | 数量 | 方式 |
|------|------|------|
| MVP（现在） | 100 | 人工精选，验证流程 |
| V1 | 300-500 | 覆盖 20 个常见场景 |
| V2 | 1000+ | 商城 API 批量接入，自动同步价格 |
| 长期 | 持续 | 用户提交 + 审核 + 供应商合作 |

### 面试话术

> "100 个是验证流程的量，不是终态。三个策略：按场景覆盖而非按品类堆量（几百个就覆盖大部分学生场景）；建数据管道接商城 API 批量获取、自动同步价格；把'搜不到'变成需求信号入口，用户提交的缺失型号就是补录优先级。数据质量始终优先于数量，因为'可信'是立身之本——1000 个没审核的数据比 100 个精挑细选的数据更危险。"
